# Observability Coverage Expansion Design

**Date:** 2026-08-15

## Goal

Repair the repository's broken Prometheus and Grafana integrations, enable the
supported metrics endpoints and monitors identified by the observability audit,
and import the recommended upstream dashboards without bypassing Flux or
creating duplicate monitoring resources.

## Scope

The work covers four independently deployable waves:

1. repair existing monitor and dashboard delivery defects;
2. enable low-risk Prometheus collection;
3. enable the higher-volume Cilium and Authentik integrations; and
4. import dashboards after their required Prometheus targets are healthy.

Each wave is committed separately. Pushing any wave requires explicit user
permission because a push triggers Flux reconciliation and changes the cluster.
No application removal, Alertmanager receiver change, Discord credential change,
or manual persistent Kubernetes patch is in scope.

## Architecture

Prometheus continues to discover ServiceMonitor, PodMonitor, and PrometheusRule
resources cluster-wide. Grafana continues to receive dashboards exclusively
through Grafana Operator `GrafanaDashboard` resources selected by the label
`dashboards: grafana`; no Grafana sidecar is added.

The target data flow is:

```text
application metrics endpoint
  -> ServiceMonitor or PodMonitor
  -> Prometheus
  -> optional PrometheusRule
  -> Alertmanager

version-pinned dashboard JSON or chart-generated dashboard ConfigMap
  -> GrafanaDashboard
  -> Grafana Operator
  -> Grafana
```

Chart-native monitor and dashboard resources are preferred when they match the
repository's Prometheus and Grafana Operator conventions. Custom resources are
added only where a chart omits the required integration or produces a
sidecar-only dashboard ConfigMap.

## Wave 1: Repair Existing Integrations

Wave 1 fixes resources that already exist but do not currently work as intended:

- change both Envoy Gateway monitor namespace selectors from `network` to
  `networking`;
- replace the two invalid Gatus `GrafanaDashboard` ConfigMap references with one
  dashboard resource that imports the generated `gatus` ConfigMap and
  `gatus.json` key;
- change Spegel dashboard delivery from `Sidecar` to `GrafanaOperator` and match
  Grafana instances labeled `dashboards: grafana`;
- add a second Victoria Logs `GrafanaDashboard` referencing the existing
  `victoria-logs-vector-k8s-monitoring` ConfigMap and
  `vector-k8s-monitoring.json` key.

## Wave 2: Enable Low-Risk Prometheus Collection

Wave 2 enables native monitoring integrations with narrow metric surfaces:

- enable ExternalDNS's existing chart ServiceMonitor;
- enable Node Feature Discovery Prometheus support, which creates its PodMonitor;
- enable cert-manager's chart ServiceMonitor;
- enable the Flux Operator ServiceMonitor and add the official Flux controller
  PodMonitor for the Flux controllers;
- enable Reloader's chart PodMonitor rather than its deprecated ServiceMonitor;
- restore Immich's ServiceMonitor using the deployed app-template chart schema
  and its existing `metrics` service port;
- add monitors for the Dragonfly operator metrics service and the Dragonfly
  data-plane admin metrics endpoint; and
- add a ServiceMonitor for promxy's `/metrics` endpoint.

The smartctl-exporter bundled rules remain disabled because the repository's
custom PrometheusRule replaces them. The kube-proxy monitor remains disabled
because the cluster uses Cilium kube-proxy replacement. Hubble remains disabled.

## Wave 3: Enable Higher-Volume Monitoring

Wave 3 is isolated so metric growth and alert behavior can be evaluated before
dashboard expansion:

- enable Cilium agent Prometheus metrics and the agent ServiceMonitor;
- enable the Cilium operator ServiceMonitor while retaining the operator's
  existing metrics endpoint; and
- enable Authentik server and worker metrics services, their ServiceMonitors,
  and Authentik's bundled Prometheus rules.

No Hubble metrics, dashboards, or components are enabled. If Authentik's bundled
rules duplicate an existing repository rule or produce unsuitable alert noise,
the rule setting is reverted independently while retaining metric collection.

## Wave 4: Import Recommended Dashboards

Wave 4 adds or completes Grafana Operator imports for:

- Tuppr;
- External Secrets;
- NVIDIA DCGM Exporter;
- Cilium Agent and Cilium Operator, using the dashboard ConfigMaps generated by
  the Cilium chart;
- Flux Cluster Stats and Flux Control Plane;
- Envoy Gateway Global, Envoy Proxy Global, Envoy Clusters, and Envoy Resources;
- Authentik;
- Node Feature Discovery; and
- Dragonfly.

The global rate-limit Envoy dashboard is excluded because that component is not
deployed. Immich, cert-manager, ExternalDNS, Reloader, autobrr, and promxy are
excluded because their upstream projects do not provide a canonical,
version-matched dashboard artifact for the deployed versions.

For chart-generated local dashboard ConfigMaps, `configMapRef` is used. For
upstream JSON, `GrafanaDashboard.spec.url` uses a release-tagged immutable URL
where one exists, with Prometheus datasource inputs mapped to the repository's
`prometheus` datasource. Tuppr uses its chart-native Grafana Operator integration.

## Validation Gates

Every wave must pass repository validation before it is eligible to push:

- render each affected chart at the repository's pinned chart version;
- run `kustomize build` for every changed application directory;
- run schema or server-side dry-run validation where the cluster supports it;
- run `git diff --check`; and
- inspect the complete wave diff for unrelated resources, Secrets, receivers,
  and credentials.

After an explicitly approved push and Flux reconciliation, each wave must pass a
live gate before the next wave begins:

- affected Flux HelmReleases and Kustomizations are Ready;
- each new ServiceMonitor or PodMonitor resolves at least one healthy target;
- Prometheus reports the targets as `up` without persistent scrape errors;
- Prometheus rule groups load without evaluation errors;
- series growth is reviewed against the pre-wave baseline; and
- no unexpected alerts remain firing.

Dashboard resources must reach `ApplySuccessful`, resolve their datasource
inputs, and show data in representative panels. A dashboard is not considered
validated merely because its custom resource exists.

## Failure Handling and Rollback

A wave stops if Flux does not become Ready, a monitor resolves no targets,
targets remain down, series growth is unexpectedly large, rule evaluation fails,
or a dashboard remains invalid or empty after its target metrics are confirmed.

Rollback is a Git revert of only the failing wave followed by an explicitly
approved push. Manual Kubernetes patches may be used temporarily for diagnosis
or verification but are not a fix because Flux will overwrite them. If only an
alert rule is noisy, disable or tune that rule without disabling otherwise
healthy metric collection.

## Success Criteria

The work is complete when all planned monitors have healthy Prometheus targets,
all enabled rule groups evaluate successfully, all recommended dashboard
resources are synchronized and show data, the two invalid Gatus dashboard
resources no longer exist, and no chart-produced dashboard intended for Grafana
Operator remains stranded in an unconsumed sidecar ConfigMap.
