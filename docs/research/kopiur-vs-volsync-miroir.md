# Research: Would Kopiur prevent the recurring VolSync + Miroir failure?

## Summary

**Not inherently.** Kopiur's default cache behavior would remove the *persistent node-local cache pin* that makes this cluster's failure recur after reboots, but its default `copyMethod: Snapshot` still creates a CSI `VolumeSnapshot`, restores it into a temporary staging PVC, and runs a node-local mover Job against that PVC. On Miroir 0.11.22, a freely scheduled mover can therefore still require a remote client attachment to a staging volume on a node without a diskful replica; configuring Kopiur's optional persistent cache on `miroir-ephemeral` can recreate essentially the same pin and failure.

Kopiur is attractive as a Kopia-native backup system, but it is alpha, young, uses an incompatible repository format from upstream VolSync/restic, and does not remove the underlying Miroir remote-attachment defect. **Do not migrate solely to fix this incident class.** First remove node-local cache placement from the present VolSync path or fix/upgrade Miroir; then evaluate Kopiur in a parallel pilot with an ephemeral (`emptyDir`) cache and explicit placement/copy-method tests.

## Findings

1. **Critical — Kopiur and the current VolSync path have the same load-bearing staging topology.** Kopiur's default `Snapshot` method: (1) creates a CSI `VolumeSnapshot`, (2) creates a temporary PVC restored from it, (3) mounts that PVC into a mover Job, and (4) deletes both staging objects after completion. `Clone` similarly creates a temporary CSI clone. This is not an in-place/object-level snapshot reader; Kopia always reads a mounted filesystem. [Kopiur copy-method documentation](https://github.com/home-operations/kopiur/blob/main/docs/copy-methods.md) VolSync restic `copyMethod: Snapshot` likewise provisions a point-in-time PVC from a `VolumeSnapshot`. [VolSync restic documentation](https://volsync.readthedocs.io/en/latest/usage/restic/)

2. **Critical — Kopiur eliminates the sticky cache pin only when its default ephemeral cache is retained.** With no cache capacity configured, Kopiur mounts `emptyDir`; with capacity and the default `Ephemeral` mode it uses a per-run generic ephemeral PVC. `Persistent` explicitly creates a stable, controller-owned **ReadWriteOnce PVC reused across runs**. The source says persistent mode assumes non-overlapping runs and is owned by the `SnapshotPolicy` for backups, so it survives individual backup CRs. [Cache resolver source](https://github.com/home-operations/kopiur/blob/main/crates/controller/src/cache.rs) [Cache API source](https://github.com/home-operations/kopiur/blob/main/crates/api/src/common/cache.rs) [Persistent cache PVC implementation](https://github.com/home-operations/kopiur/blob/main/crates/controller/src/io/mover.rs) Thus:
   - omit `mover.cache.capacity` (best for this failure analysis) and the cache cannot pin the mover;
   - a sized generic-ephemeral cache does not persist across reboots/runs, but a local `WaitForFirstConsumer` class still participates in per-run placement;
   - `mode: Persistent` + `storageClassName: miroir-ephemeral` recreates the problematic long-lived, node-local RWO anchor.

3. **Critical — removing the cache pin does not guarantee a diskful staging attachment.** Kopiur describes a brand-new staged PVC as “unheld,” so its mover “schedules freely” and is decoupled from the application node. [Snapshot staging behavior](https://github.com/home-operations/kopiur/blob/main/docs/copy-methods.md#snapshot--point-in-time-csi-snapshot-default) Its RWO co-location logic pins a mover only when it can discover an existing holder, PV node affinity, or attached `VolumeAttachment`; an unheld RWO PVC in default `Auto` mode is free to schedule. [Co-location source](https://github.com/home-operations/kopiur/blob/main/crates/controller/src/io/colocation.rs) In this cluster, free scheduling can still select a node with no diskful replica of the `miroir-replicated` stage, invoking the same Miroir remote-client path and its `Can not drop the bitmap when both sides have a disk` failure. Kopiur therefore lowers recurrence caused by a sticky cache, but **does not bypass or repair Miroir's attachment path**.

4. **High — Kopiur provides placement controls, but no dynamic “choose a diskful replica of this Miroir volume” integration.** Repository-wide `spec.moverDefaults` supports `nodeSelector`, tolerations, affinity, and `sourceColocation` (`Auto`, `Required`, `Disabled`). These settings flow to movers; the API source explicitly says there is no per-recipe override for node selector/tolerations/affinity today. [Mover API source](https://github.com/home-operations/kopiur/blob/main/crates/api/src/common/mover.rs) Static affinity can restrict backups to known data nodes, but cannot identify which nodes hold diskful replicas of each newly restored staging volume. It can therefore reduce exposure or make Jobs unschedulable, not prove avoidance.

5. **High — staging on another class is possible but needs a Miroir-specific proof, not assumption.** `spec.staging.storageClassName` may place a Snapshot/Clone stage on another StorageClass only when it uses the **same CSI driver**; Kopiur rejects a driver mismatch. It also supports changing stage access modes. [Staging overrides](https://github.com/home-operations/kopiur/blob/main/docs/copy-methods.md#staging-overrides) A potential experiment is a WFFC, single-replica Miroir staging class with no persistent cache so the mover and stage are created together. However, Kopiur automatically deletes the stage and `VolumeSnapshot` at terminal completion, while this repository's documented Miroir 0.11.22 safeguards require retaining temporary restore PVCs/snapshots until binding and content verification and clearing activation-skip on restored LVs. That makes this an unsafe production assumption until exercised and reconciled with those safeguards.

6. **Medium — `Direct` avoids the failing snapshot-stage topology, at a consistency cost.** `copyMethod: Direct` mounts the live PVC read-only and Kopiur co-locates the mover with the current RWO holder to avoid multi-attach. It creates no CSI snapshot or staging clone. It is not a point-in-time capture: files can change throughout the read. Snapshot/Clone are block-level point-in-time and crash-consistent; application consistency requires before/after hooks that quiesce the workload. [Copy-method and consistency matrix](https://github.com/home-operations/kopiur/blob/main/docs/copy-methods.md) Direct is therefore a plausible temporary pilot for low-write/file workloads, not a like-for-like replacement for database snapshot backups.

7. **Medium — backup/restore UX is materially richer than upstream VolSync/restic.** Kopiur separates `SnapshotPolicy` (recipe), `Snapshot` (invocation/catalog row), and `SnapshotSchedule` (cron); supports manual/external triggers; restores a selected snapshot to a new or existing PVC; and can act as a volume-populator source through `PVC.spec.dataSourceRef`. It also materializes repository snapshots as Kubernetes catalog objects. [README and CRD overview](https://github.com/home-operations/kopiur) [Restore example](https://github.com/home-operations/kopiur/blob/main/deploy/examples/03-restore-by-backup.yaml) Snapshot/Clone is point-in-time crash-consistent, hooks can add application consistency, and multi-PVC selectors can use CSI `VolumeGroupSnapshot` for same-instant capture—requiring external-snapshotter 8.2+, feature gates, a group class, driver support, and cluster scope. [Multi-PVC example](https://github.com/home-operations/kopiur/blob/main/deploy/examples/04-multi-pvc-selector.yaml)

8. **Medium — scheduling and lifecycle are stronger, but add CRD/operator complexity.** `SnapshotSchedule` supports cron, deterministic `H`, jitter, timezone, and `runOnCreate: false`; the worked example uses `H 2 * * *` with 30-minute jitter. [Scheduled backup example](https://github.com/home-operations/kopiur/blob/main/deploy/examples/01-single-pvc-scheduled.yaml) Successful retention is GFS (`keepLatest`, hourly/daily/weekly/monthly/annual); pruning deletes `Snapshot` CRs outside the retained set, whose finalizers normally delete their Kopia snapshots. Repository `Maintenance` handles Kopia quick/full maintenance and ownership, and is default-managed unless overridden. [Architecture ADR](https://github.com/home-operations/kopiur/blob/main/docs/adr/0003-kopiur-rust-operator.md) This is more explicit than VolSync, but makes deletion policy, adoption, maintenance ownership, CRD upgrades, and repository credentials part of the migration runbook.

9. **Medium — repository support is broad, but upstream VolSync/restic history cannot migrate.** Kopiur supports S3-compatible storage, Azure, GCS, B2, filesystem PVC/NFS, SFTP, WebDAV, rclone, and experimental native Google Drive; namespaced `Repository` and shared, namespace-gated `ClusterRepository` are supported. [Repository documentation](https://github.com/home-operations/kopiur/blob/main/docs/repositories.md) Its `kubectl kopiur migrate volsync` command translates manifests, but upstream VolSync **restic and Kopia repository formats are incompatible**. A new empty Kopia repository is required and VolSync must remain until Kopiur builds sufficient recovery history. Only the perfectra1n VolSync Kopia fork can be adopted in place. Some Restic semantics, such as `retain.within`, have no direct equivalent. [VolSync migration documentation](https://github.com/home-operations/kopiur/blob/main/docs/cli/migrate-volsync.md)

10. **High — operational maturity is not yet equivalent to VolSync.** The project labels itself **alpha** with a `v1alpha1` API that may change. [README](https://github.com/home-operations/kopiur) The current checked source/chart is 0.10.3 and the GitHub release API shows 0.10.3 published on 2026-08-18; the repository itself was created in June 2026. [Release 0.10.3](https://github.com/home-operations/kopiur/releases/tag/0.10.3) Releases have already required special CRD handling: Helm does not upgrade CRDs, and the 0.5.x→0.6.0 transition could cascade-delete CR objects unless CRDs were pinned. [Upgrade guide](https://github.com/home-operations/kopiur/blob/main/docs/upgrade.md) A current 0.10.3 restore issue reports missing mover RBAC for reading the base `Restore`, breaking deterministic “latest” resolution on retries (restores may still complete). [Issue #401](https://github.com/home-operations/kopiur/issues/401) Another open issue covers restore readiness timing with missing GitOps referents. [Issue #393](https://github.com/home-operations/kopiur/issues/393) There are no primary-source Kopiur issues demonstrating Miroir/DRBD compatibility or this bitmap failure.

11. **Medium — cluster prerequisites and permissions must be checked.** The install guide says Kubernetes 1.24+ for populator support, while the current 0.10.3 chart declares Kubernetes 1.32+ because WatchList is enabled by default; the chart note says it can be disabled, but the declared chart floor still matters to Flux/Helm rendering. Cluster scope is required for Snapshot/Clone staging and cluster repositories; namespaced installs refuse those features. Snapshot mode also requires snapshot-controller and a matching `VolumeSnapshotClass`. [Install guide](https://github.com/home-operations/kopiur/blob/main/docs/install.md) [Chart README](https://github.com/home-operations/kopiur/blob/main/deploy/helm/kopiur/README.md) Privileged movers require Kopiur's own namespace annotation (`kopiur.home-operations.com/privileged-movers: "true"`), not the existing VolSync annotation, so namespace manifests would need additions. [Mover permissions](https://github.com/home-operations/kopiur/blob/main/docs/movers.md#privileged-movers)

## Comparison focused on the failure

| Property | Current VolSync/restic | Kopiur | Effect on this failure |
|---|---|---|---|
| Snapshot clone/stage | CSI snapshot → PiT PVC | CSI snapshot → temporary staged PVC | Same dependency on Miroir snapshot restore and attachment |
| Mover | Short-lived pod/Job mounting stage | Short-lived Job in workload namespace | Same node-local Kubernetes execution model |
| Cache | Persistent cache PVC; currently node-local | `emptyDir` by default; optional ephemeral PVC; optional persistent RWO PVC | Default removes sticky pin; persistent + `miroir-ephemeral` recreates it |
| Scheduling | Cache/PVC topology influences scheduler | Repo-wide affinity plus RWO co-location logic | No Miroir diskful-replica-aware placement |
| CSI snapshots | Required by current copy method | Required by default Snapshot method | No bypass |
| Repository | Restic | Kopia; many backend types | Requires new repository and overlapping retention |
| Restore | ReplicationDestination/restic restore | Explicit snapshot catalog, PVC restore, populator | Better UX, but still mover/PVC based |

## Verdict and recommended path

**Verdict: Kopiur would eliminate the recurring cache-pin trigger only if deployed without a persistent node-local cache. It does not eliminate the underlying VolSync+Miroir failure class; with `copyMethod: Snapshot` it can still hit Miroir's remote client attachment, and with a persistent `miroir-ephemeral` cache it can recreate the same topology almost exactly.** Treat claims that it is a direct fix as unsupported.

Recommended path for this cluster:

1. **Keep VolSync as the production backup system for now.** Remove the node-local cache as a scheduling anchor—prefer a non-node-local/replicated cache class or another tested cache arrangement—and separately pursue a Miroir fix/upgrade for the remote attachment error. Do not trade a known failure for an alpha backup migration without preserving restore coverage.
2. **Open a parallel Kopiur pilot, not a cutover**, after confirming Kubernetes/chart prerequisites. Use a new Kopia repository; keep all Restic history and VolSync schedules until the Kopiur retention window and test restores are sufficient.
3. In the pilot, **omit cache capacity entirely** so the cache is `emptyDir`; explicitly set `copyMethod` in Git (never rely on changing defaults). Test repeated backup/restore runs across full node reboots and deliberately force movers onto nodes with and without diskful stage replicas.
4. Test two policies separately: (a) `Snapshot` on `miroir-replicated` to prove whether the Miroir failure remains; (b) `Direct` for appropriate low-write workloads to prove the no-stage escape path. Do not use Direct for databases without an accepted consistency plan.
5. Do **not** productionize a `miroir-ephemeral` staging override or Kopiur's automatic stage cleanup until it is reconciled with this repository's Miroir 0.11.22 restore safeguards (temporary PVC/snapshot retention, activation-skip clearing, and post-cleanup LV audit).
6. Reassess migration only after successful reboot/failure-injection tests, restore-content validation, no activation-skip/orphan snapshot LVs, and closure/workaround of relevant Kopiur restore issues. Pin the OCI chart/images and manage CRD upgrades explicitly through Flux.

## Gaps

No Kopiur or Miroir primary-source issue documents this exact cross-project bitmap failure, and static source review cannot prove how Miroir 0.11.22 will place/attach a particular Kopiur staging PVC. The decisive next evidence is a controlled pilot matrix across cache modes, staging classes, mover nodes, and reboots, with Miroir volume/replica state captured for every run.
